# На проводе у всех моих реакций `chosen_order = 0` — порядок постановки теряется

**Статус:** открыт, долг назван (не закрыт кодом).
**Дата фиксации:** ветка `fix/reactions-limit-and-echo`, при вводе лимита
«сколько реакций ставит один пользователь» — 2026-09-06.

## Что происходит

`chosen_order` у оригинала — ПОРЯДКОВЫЙ НОМЕР реакции среди моих на этом
сообщении (`reactionCount#a3d1cb80 chosen_order:flags.0?int`), и именно им
клиент решает, какая из моих реакций самая старая
(tweb `src/lib/appManagers/appReactionsManager.ts:733-751`).

Мы шлём его константой: `NewReactionCount`
(`internal/domain/mtmessage.go:1043-1050`) ставит `chosen_order = 0` каждой
реакции, у которой `mine`, потому что витрина `domain.ReactionCount` несёт
булево «моя», а не номер. Порядок в базе при этом ЕСТЬ —
`reactions.created_at`, — просто он не доезжает до клиента.

## Чем это платится

Серверное вытеснение (`usecase/chat/reaction.go::evictExcessReactions`)
работает правильно: оно читает `created_at` напрямую. А клиентское —
оптимистичное, до ответа сервера — после ПЕРЕЗАГРУЗКИ страницы выбирает
жертву не по времени постановки, а по порядку чипов в агрегате (все номера
нулевые, сортировка стабильна), то есть по убыванию счётчика.

Видно это только у премиума: в базовом лимите слот один, и жертва там
единственная, какой её ни выбирай.

Кадром это НЕ ЛЕЧИТСЯ, и первая редакция долга («кадр приносит серверный
состав и картинка сходится») была неверна. Сходится только СОСТАВ чипов;
пометка «моя» — нет. Разбор по шагам: свои реакции A(старейшая), B, C, клик
по D. Сервер снимает A, клиент — C (номера-то нулевые). Кадр несёт
абсолютный агрегат {B, C, D} и НЕ несёт `chosen_order` — он пер-зрительский
и в общем теле его не бывает (`pFlags.min`), поэтому `mergeReactions`
(`web-client/src/core/reactions/messageReactions.ts`) восстанавливает мой
выбор из ПРЕДЫДУЩЕГО состояния, а там после локального вытеснения числятся
{A, B, D}. Итог: A исчезает (верно), C остаётся в ленте с правильным
счётчиком, но НЕ помеченной моей — при том что на сервере она моя.

Само это состояние не проходит: каждый следующий кадр несёт тот же агрегат
без `chosen_order` и слияние снова возьмёт мой выбор из уже испорченного
предыдущего. Лечится только новым кликом по этому чипу или перезагрузкой
истории — там `Mine` считает уже сервер (`ReactionsFor`, viewerID).

## Что делать

`ReactionsFor` (`internal/adapter/repo/postgres/reactionsrepo.go`) уже
группирует по сообщению — добавить туда номер зрителя,
`row_number() OVER (PARTITION BY re.user_id ORDER BY re.created_at)` для
строк `re.user_id = $viewer`, и провести его через `domain.ReactionCount`
(`Mine bool` → номер) в `NewReactionCount`. Задевает витрину, провод и
тесты обеих сторон, поэтому отдельной задачей.

**Критерий готовности:** после перезагрузки страницы у премиума с тремя
своими реакциями `chosen_order` = 0,1,2 в порядке постановки, и четвёртый
клик локально снимает ровно тот чип, который снимет сервер.
