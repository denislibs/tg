# Этап 1B.2: операции над окном сообщений — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ввести операционный протокол для домена сообщений и перевести на него **один** путь — `new_message`. Остальные десять типов кадров переезжают следующим планом, когда протокол проверен на живом.

**Architecture:** Воркер остаётся единственным местом, где апдейт **интерпретируется**. После применения к своему SSOT он рассылает не сырой кадр, а **операцию** — что именно изменилось в окне. Главный поток операцию только переигрывает. Это порт механизма tweb, где `historyStorage` зеркалится вызовами методов `SlicedArray` (`appMessagesManager.ts:7012-7088`), а на главном потоке они исполняются как есть (`apiManagerProxy.ts:286-297`).

**Tech Stack:** TS strict, vitest + happy-dom, Zustand, SharedWorker + rootScope.

## Почему только один путь

Разведка составила таблицу двойного применения: 11 типов кадров, каждый применяется и в воркере (`messages.cacheX`), и заново на главном потоке (`messagesStore.applyX`). Перевести все сразу — значит одним коммитом поменять поведение всего домена, где живут оптимистичная отправка, треды, альбомы и секретные чаты. `new_message` выбран первым, потому что он самый горячий, единственный, кто вставляет в срез (`cacheLive` → `sa.unshift`), и именно на нём сходится слияние с оптимистикой.

Страховка уже есть: этап 1B.1 закрыл пинами дедуп окна, жизненный цикл pending-кадров, outbox и коллизию `tentativeSeq`.

## Global Constraints

- **Один интерпретатор.** После этого этапа кадр `new_message` разбирается ровно в одном месте — в воркере. Главный поток не должен знать структуру кадра: он принимает операцию.
- **Поведение не меняется.** Это перекладывание ответственности, а не смена семантики. Все существующие тесты домена (`messagesStore.*.test.ts`, `useMessageWindow.test.ts`, `storeProjection.pending.test.ts`, `messagesManager.test.ts`) обязаны пройти **без единой правки**. Правка любого из них — сигнал, что поведение поехало: остановиться и сообщить.
- **Инвариант дедупа, ставший несущим в 1B.1:** неподтверждённый бабл — это `clientId` + `id < 0` (`messagesStore.ts:62-64`). Операции обязаны его сохранять: сообщение до ack остаётся с отрицательным `id`.
- Операции типизированы и выводятся из одного объявления; пропуск ветки в переигрывателе обязан ловиться компилятором (как `LoggedWsType` в `eventCatalog.ts`).
- `SlicedArray` (`src/core/history/slicedArray.ts`) — вендор-островок с `@ts-ignore`; **не трогать**.
- Комментарии по-русски, в стиле окружающего кода.
- Команды из `web-client/`: `npm test`, `npm run typecheck`, `npx oxlint <файлы>`, `npm run build`.
  `npm run lint` выходит с кодом 1 и на main (вендореный `middleware.ts`) — ворота: не добавлять НОВЫХ находок.

### Task 2: Каталог операций окна

**Files:**
- Create: `web-client/src/core/realtime/messageOps.ts`
- Test: `web-client/src/core/realtime/messageOps.test.ts`

**Interfaces:**
- Produces:
  ```ts
  /** Операция над окном сообщений: что именно изменилось. Порождает ТОЛЬКО воркер
   *  (он единственный интерпретирует кадр), переигрывает — только проектор. */
  export type MessageOp =
    | { op: 'insert'; key: string; msg: Message }   // key — winKey окна
    | { op: 'replace'; key: string; msg: Message }
    | { op: 'remove'; key: string; msgId: number }

  /** Применить операцию к списку сообщений окна. Чистая функция — вся семантика
   *  дедупа/слияния живёт здесь, поэтому её можно тестировать без стора. */
  export function applyOp(msgs: Message[], op: MessageOp): Message[]
  ```
- Consumes: `Message` из `../models`, `dedupAsc`/`dedupKey` — вынести из `messagesStore.ts` сюда, если это не меняет их поведение (проверяется существующими пинами дедупа); если вынести нельзя — импортировать и сказать об этом в отчёте.

**Почему список, а не стор.** `applyOp` работает над массивом сообщений, а не над Zustand-стором: так её можно прогнать в тестах без поднятия стора, а проектор останется тонким. Это же даёт будущему Solid-острову переиспользование без переписывания.

- [ ] **Step 1: Написать тесты** на `applyOp` — каждый случай отдельно:
  1. `insert` нового сообщения → добавлено, порядок по возрастанию `seq`;
  2. `insert` сообщения, чей `clientId` совпал с неподтверждённым баблом → бабл заменён, в списке один элемент, `clientId` сохранён (это семантика `applyIncoming`: `messagesStore.ts:~322-325`);
  3. `insert` сообщения, чей `id` уже есть (ack-then-echo) → дубля нет, список не изменился;
  4. `insert` сообщения с тем же `seq`, что у неподтверждённого бабла, но БЕЗ совпадения `clientId` → **оба** остаются (инвариант, починенный в 1B.1);
  5. `replace` существующего → заменено, позиция по `seq` сохранена;
  6. `replace` отсутствующего → список не изменился (no-op);
  7. `remove` существующего по `msgId` → удалено;
  8. `remove` отсутствующего → no-op, та же ссылка на массив (важно для мемоизации).

- [ ] **Step 2: RED** (модуля нет), затем реализация. **GREEN.**

- [ ] **Step 3: `npm test`, typecheck, oxlint. Commit** — `feat(messages): каталог операций над окном + чистый applyOp`

### Task 3: Воркер порождает операцию для new_message

**Files:**
- Modify: `web-client/src/core/worker.ts` (`routeNewMessage`)
- Modify: `web-client/src/core/managers/messagesManager.ts` (`cacheLive` возвращает результат)
- Modify: `web-client/src/lib/rootScope.ts` (событие `rt:message_op` в каталоге)
- Test: `web-client/src/core/managers/messagesManager.test.ts` (дописать)

**Interfaces:**
- Produces: `cacheLive(evt): MessageOp[]` — возвращает операции, которые кадр породил в SSOT (по одной на затронутое окно: основное и, для тред-сообщения, окно треда). Пустой массив, если ничего не изменилось.
- Consumes: `MessageOp` из `../realtime/messageOps`.

**Важно.** `cacheLive` сейчас вставляет только в срез, уже державший низ истории (`messagesManager.ts:~493-497`) — окно, не догруженное до низа, пропускается. Операции обязаны отражать **ровно то же**: для пропущенного окна операция не порождается. Иначе главный поток получит вставку туда, где воркер её не сделал, и представления разъедутся — то самое расхождение, ради устранения которого всё затевается.

- [ ] **Step 1: Тест на `cacheLive`** — дописать в существующий файл: кадр обычного сообщения → одна операция `insert` с ключом основного окна; кадр тред-сообщения при обоих загруженных срезах → две операции; кадр в окно, не державшее низ → операций нет. RED, затем реализация.

- [ ] **Step 2: Воркер рассылает.** В `routeNewMessage` — `const ops = messages.cacheLive(e)`, затем `broadcast(RT.messageOp, { ops }, meta)` **в дополнение** к существующему `broadcast(RT.newMessage, e, meta)`. Оба кадра пока летят: старый путь остаётся рабочим, новый добавляется — это позволяет переключить проектор отдельной задачей и откатить одной строкой.

- [ ] **Step 3: Событие в каталоге** `BroadcastEvents` (`rootScope.ts`): `[RT.messageOp]: [{ ops: MessageOp[] }, EventMeta?]`, имя `messageOp: 'rt:message_op'` в `RT` (`events.ts`).

- [ ] **Step 4: `npm test` (всё зелёное, ни один тест не правился), typecheck, oxlint, build. Commit** — `feat(messages): cacheLive возвращает операции, воркер их рассылает`
