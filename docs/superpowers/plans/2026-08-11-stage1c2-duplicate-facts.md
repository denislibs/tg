# Этап 1C.2: ликвидация дублей фактов — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** У каждого факта — один владелец. Воркер владеет, витрина зеркалит; второго независимого вывода не остаётся.

**Architecture:** 1C.1 дал воркеру собственный инстанс `RootScope` (`core/realtime/workerScope.ts`) — то есть способ рассылать типизированные события во все вкладки. До сих пор он рассылал только апдейты чатов. Теперь через ту же шину поедут **факты**: воркер, вычислив значение, публикует его; витрина применяет и больше нигде не выводит сама.

**Tech Stack:** TS strict, vitest + happy-dom, SharedWorker + rootScope.

Читателей `meId` в компонентах — 68, но все через селектор стора. Меняется писатель, не читатели.

## Global Constraints

- **Один владелец — значит один вывод.** После задачи в витрине не должно остаться кода, который вычисляет факт самостоятельно; допустимо только применение пришедшего значения.
- **Поведение не меняется.** Все существующие тесты обязаны пройти **без единой правки**. Правка любого — стоп и BLOCKED с указанием инварианта.
- **Оптимистичность сохраняется.** Там, где витрина сегодня показывает результат своего действия мгновенно (смена имени, покупка премиума), скорость отклика не должна упасть. Если владение воркером делает отклик медленнее — это регрессия, а не «зато чисто»; останавливайся и говори.
- **Каждая новая строка проводки — по норме `web-client/CLAUDE.md`** (раздел «Тесты»): либо тест, краснеющий на её удалении, либо пометка комментарием прямо у строки с причиной. Норма построчная, список файлов в ней — подсказка, не периметр.
- Новые события — в каталоге `BroadcastEvents` (`src/lib/rootScope.ts`), типизированно. Ре-эмит принятого из воркера — только `dispatchEventSingle`, иначе кольцо.
- Комментарии по-русски, в стиле окружающего кода.
- Команды из `web-client/`: `npm test`, `npm run typecheck`, `npx oxlint <файлы>`, `npm run build`.
  `npm run lint` выходит с кодом 1 и на чистом main — ворота: не добавлять НОВЫХ находок в изменённых файлах.
- **Git-гигиена:** только точечный `git add <файлы>` + `git commit`. Запрещены `git reset`, `git rebase`, `git commit --amend`, `git checkout`/`restore`, `git stash`, `git add -A`/`.`, `git commit -a`.

- [ ] **Step 1: Инвентаризация.** Выпиши все восемь мест: что каждое кладёт в `me` и откуда берёт. Часть — ответы RPC (профиль обновлён, премиум куплен), часть — гидрация. Для каждого реши: остаётся оптимистичным на витрине или уезжает в воркер.

- [ ] **Step 2: Событие.** Завести в каталоге типизированное событие «me изменился» с payload — полным `User | null`. Воркер публикует его: при первом выводе (`tokens.ready().then(auth.me())`) и при каждом изменении, инициированном RPC-путями.

- [ ] **Step 3: Витрина — только применение.** `setMe` остаётся публичным API стора, но зовётся **только** из проектора по событию. - [ ] **Step 4: Тесты.** Пин: воркер опубликовал `me` → `meId` в сторе обновился. Второй пин: в витрине не осталось независимого вывода — по образцу `stores/noManualOrder.test.ts` (текстовый скан на прямые вызовы `setMe` вне проектора, с allow-list обоснованных исключений).

## Self-Review

- Порядок задач — по возрастанию связности: `meId` (одно значение, много читателей), пиры (коллекция со своей инвалидацией), токен (короткоживущее значение с расписанием и гонкой старта).
- Задача 1, Шаг 3 сознательно допускает исход «оставить оптимистичное применение плюс событие»: потеря отзывчивости интерфейса — худшая цена, чем оставшийся дубль, и решать это надо по коду, а не по принципу.
- **Вне объёма:** гранулярность подписки и фаза коммита (план 1.6); кросс-табовое зеркало State — проверено ранее, это точный порт tweb, трогать нечего; `pinnedOrders`/`drafts`/`folders` — отдельная задача, если найдётся расхождение.
