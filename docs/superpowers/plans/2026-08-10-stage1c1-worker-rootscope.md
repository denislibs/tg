# Этап 1C.1: воркерный rootScope + прополка портов — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Дать воркеру полноценный инстанс `RootScope` вместо голой функции `broadcast` и научить его замечать закрытые вкладки — так, как это делает tweb.

**Architecture:** Сегодня в воркере шина односторонняя: `broadcast(event, payload, meta)` (`worker.ts:130`) только рассылает наружу. Локальных подписчиков в воркере нет, поэтому менеджеры не могут слушать друг друга — связи между ними прошиты параметрами конструктора. В tweb тот же модуль `rootScope.ts` собирается в **оба** бандла, и в воркерном инстансе `dispatchEvent` = локальные слушатели + отправка в порт (`rootScope.ts:280-290`). Мы уже перенесли этот класс в Этапе 1A (`src/lib/rootScope.ts`) — осталось создать второй инстанс на воркерной стороне и завести его порт на веер по всем вкладкам.

Второй кусок — прополка `ports`. Массив (`worker.ts:129`) только растёт: события продолжают лететь в порты мёртвых вкладок. tweb решает это **Web Locks**, а не пингами, и в коде прямо написано почему: `// ! Can't rely on ping because timers can be suspended` (`superMessagePort.ts:250`). Вкладка берёт лок со случайным id и сообщает id воркеру; воркер запрашивает **тот же** лок — браузер отдаст его только когда вкладка умерла, и это и есть сигнал отключения.

**Tech Stack:** TS strict, vitest + happy-dom, SharedWorker, Web Locks API.

## Что показала разведка (факты, на которых стоит план)

- `broadcast` раздаётся как зависимость в `messages`, `realtime`, `secret`, `persist`, `media` и вызывается напрямую ещё в ~15 местах `worker.ts`. Это единственный способ, которым воркер говорит наружу.
- Приём события **от** вкладки уже реализован (`worker.ts:344-347`, `smp.onAny`) и ретранслирует всем, кроме источника — порт tweb `index.worker.ts:116-119`. Локальным воркерным слушателям он при этом ничего не отдаёт, потому что их не существует.
- `helpers/listenMessagePort.ts` уже вендорен, но используется только островком tlottie (со своим `lib/twebMessagePort.ts`). Наш рабочий транспорт — `src/rpc/superMessagePort.ts`, 136 строк, три вида задач (`invoke`/`result`/`event`). Лок-механизма в нём нет.
- Два независимых дебаунса рефетча `/chats` по 300 мс: `storeProjection.ts:33-40` (два вызова, строки 135 и 223) и `refetchSubscriber.ts:16-22` (вызов на строке 46). Таймеры разные, поэтому срабатывание из обеих зон даёт **два** параллельных `/chats`.

## Global Constraints

- **Форма — как в tweb.** Класс `RootScope` не форкать и не копировать: воркерный инстанс создаётся из того же `src/lib/rootScope.ts`. Если модуль не поднимается в воркерном контексте — чинить импорты, а не заводить второй класс.
- **Никаких колец.** Событие, принятое из вкладки, в воркере применяется через `dispatchEventSingle` (локально) и ретранслируется **остальным** портам. Источнику не отправляется никогда. Обратная отправка из локального обработчика запрещена.
- **Поведение не меняется.** Все существующие тесты обязаны пройти **без единой правки**. Правка любого — стоп и сообщение (BLOCKED) с указанием, какой инвариант поехал.
- **Web Locks — с фолбэком.** `navigator.locks` есть не везде (и отсутствует в части тестовых окружений). Нет API — фолбэк на `beforeunload`-кадр, ровно как tweb (`superMessagePort.ts:231-235`). Отсутствие обоих не должно ронять вкладку.
- `src/lib/twebMessagePort.ts`, `src/helpers/*` — вендор, не трогать.
- Комментарии по-русски, в стиле окружающего кода; ссылки на строки tweb в комментариях приветствуются (мы так уже пишем).

### Task 1: Воркерный инстанс RootScope вместо `broadcast`

**Files:**
- Modify: `web-client/src/lib/rootScope.ts` (сделать модуль пригодным для обоих контекстов; экспортировать фабрику)
- Modify: `web-client/src/core/worker.ts` (создать инстанс, заменить `broadcast`)
- Test: `web-client/src/lib/rootScope.worker.test.ts` (создать)

**Interfaces:**
- Produces:
  ```ts
  // src/lib/rootScope.ts — дефолтный экспорт остаётся главнопоточным синглтоном.
  // Воркеру нужен СВОЙ инстанс того же класса:
  export function createRootScope(): RootScope
  ```
  `RootScope.setPort` уже есть; воркер передаёт в него веер по всем портам:
  ```ts
  const workerScope = createRootScope()
  workerScope.setPort({ emit: (event, payload, meta) => { for (const p of ports) p.emit(event, payload, meta) } })
  ```
- Consumes: существующий класс `RootScope` и каталог `BroadcastEvents` (Этап 1A).

**Важно.** `broadcast` сегодня объявлен ПОСЛЕ менеджеров, а те дёргают его лениво через стрелки (см. комментарии `worker.ts:82,87,98,122`). Порядок инициализации сохранить: `workerScope` создаётся там же, где сейчас `broadcast`, а менеджеры продолжают получать ленивую стрелку — теперь она зовёт `workerScope.dispatchEvent`.

- [ ] **Step 1: Проверить, поднимается ли `rootScope.ts` в воркере.** Модуль тянет `@core/realtime/events`, `@core/models`, `@stores/foldersStore` и др. Если хоть один импорт значений (не типов) утаскивает DOM/React — это выяснится сборкой. Импорты типов безопасны. Если найдётся значение-импорт с DOM-зависимостью — заменить на `import type` (они и используются только как типы) и сказать в отчёте, какой именно.

- [ ] **Step 2: Экспортировать фабрику.** Добавить `export function createRootScope(): RootScope { return new RootScope() }`. Дефолтный экспорт (главнопоточный синглтон) не трогать.

- [ ] **Step 3: Заменить `broadcast` в `worker.ts`.** Создать `workerScope`, завести ему порт-веер, а `broadcast` оставить **тонкой стрелкой** над ним:
  ```ts
  const broadcast = (event: string, payload: unknown, meta?: EventMeta) =>
    workerScope.dispatchEvent(event as keyof BroadcastEventsListeners, payload as never, meta as never)
  ```
  Так все ~20 существующих вызовов и переданные менеджерам зависимости остаются как есть — диff минимальный, а точка применения одна. Переименование вызовов в объём задачи НЕ входит.

- [ ] **Step 4: Приём кадра от вкладки — локально + остальным.** В `bind()` (`worker.ts:344-347`) сегодня `smp.onAny` только ретранслирует. Теперь: сначала `workerScope.dispatchEventSingle(...)` (локальные воркерные слушатели), затем ретрансляция **всем портам, кроме источника**. Порядок именно такой: локальный слушатель может поправить SSOT до того, как соседние вкладки увидят кадр. `dispatchEvent` здесь НЕ звать — он ушёл бы в веер и вернулся источнику (кольцо).

- [ ] **Step 5: Тесты.** Харнес — фейковые порты (объекты с `emit`-шпионом). Обязательные случаи, каждый обязан различать исправную и сломанную реализацию:
  1. `workerScope.dispatchEvent(...)` → событие получили ВСЕ порты, и локальный подписчик воркера тоже;
  2. кадр от вкладки A → локальный подписчик воркера вызван РОВНО один раз; порт B получил; порт A НЕ получил;
  3. `meta` доезжает и в веере, и в ретрансляции (пин раскладки из 1A.1);
  4. локальный воркерный подписчик, который сам зовёт `dispatchEvent` — не порождает бесконечного кольца (счётчик отправок конечен).

- [ ] **Step 6: Доказать, что тесты кусаются.** По очереди внести две мутации, каждый раз убедиться в красноте и вернуть файл: (а) в шаге 4 заменить `dispatchEventSingle` на `dispatchEvent`; (б) снять исключение источника в ретрансляции. Привести реальные красные выводы. Если мутация НЕ покраснела — тест недостаточен, дописать и сказать об этом в отчёте.

- [ ] **Step 7: `npm test` (весь набор, без правок существующих), typecheck, oxlint, build. Commit** — `feat(worker): воркерный инстанс rootScope вместо голой функции broadcast`

### Task 2: Прополка `ports` — Web Locks по порту tweb

Массив `ports` (`worker.ts:129`) не чистится никогда. Каждая закрытая вкладка оставляет мёртвый порт, в который до конца жизни воркера летят все события.

**Files:**
- Modify: `web-client/src/rpc/superMessagePort.ts` (задача `lock`, хук отключения)
- Modify: `web-client/src/core/worker.ts` (снятие порта из `ports`)
- Modify: `web-client/src/client/bootstrap.ts` (вкладка берёт лок и сообщает id) — **точное место найти по коду**, это сторона, создающая `SuperMessagePort` к воркеру
- Test: `web-client/src/rpc/superMessagePort.lock.test.ts` (создать)

**Interfaces:**
- Produces (в `superMessagePort.ts`):
  ```ts
  // Новый вид задачи в union Task:
  | { kind: 'lock'; id: string }

  // На воркерной стороне:
  setOnPortDisconnect(cb: () => void): void
  ```
- Consumes: `navigator.locks` (Web Locks API).

**Механизм (порт tweb `superMessagePort.ts:220-236` + `:505-515`).**
1. Вкладка при подключении порта генерирует случайный `id`, вызывает `navigator.locks.request(id, () => promiseЖивущийПокаЖиваВкладка)` и отправляет воркеру `{kind:'lock', id}`.
2. Воркер, получив `lock`, сам зовёт `navigator.locks.request(id, () => { /* вкладка умерла */ })`. Пока вкладка держит лок, колбэк не выполняется. Как только вкладка закрылась — лок освобождается, колбэк воркера срабатывает, порт отцепляется.
3. Фолбэк без `navigator.locks`: вкладка на `beforeunload` шлёт `{kind:'lock', id:''}`-эквивалент — в tweb это отдельная задача `close`; у нас достаточно того же кадра с пустым id, трактуемого как немедленное отключение. Решение задокументировать комментарием.

- [ ] **Step 1: Найти сторону вкладки.** `grep` по `new SuperMessagePort` — где создаётся порт к SharedWorker. Это `src/client/*`; точный файл определить по коду, не по этому плану.

- [ ] **Step 2: Транспорт.** Добавить `kind: 'lock'` в union `Task`, обработку на приёмной стороне и `setOnPortDisconnect`. При отключении: снять слушатель, закрыть порт, дёрнуть колбэк. Идемпотентность обязательна — повторное отключение того же порта не должно звать колбэк дважды.

- [ ] **Step 3: Воркер.** В `bind()` подписаться: `smp.setOnPortDisconnect(() => { indexOfAndSplice(ports, smp) })`. Использовать уже вендореный `helpers/array/indexOfAndSplice.ts` — он для этого и лежит.

- [ ] **Step 4: Вкладка.** Взять лок и отправить его id сразу после создания порта. Ветку `'locks' in navigator` и фолбэк `beforeunload` — обе.

- [ ] **Step 5: Тесты.** Web Locks в happy-dom нет — подставить фейковый `navigator.locks` (объект с `request`, отдающий управляемый промис). Случаи:
  1. вкладка подключилась → воркер запросил лок с тем же id;
  2. лок освободился → порт ушёл из `ports`, последующий `dispatchEvent` в него не пишет;
  3. отключение идемпотентно (двойное срабатывание не роняет и не чистит лишнего);
  4. нет `navigator.locks` → используется фолбэк, кадр `beforeunload` отцепляет порт;
  5. живая вкладка НЕ отцепляется (лок удерживается).

- [ ] **Step 6: Доказать укус** — мутация «`setOnPortDisconnect` не вызывается» и мутация «`indexOfAndSplice` заменён на no-op» дают красноту. Привести выводы, вернуть файл.

- [ ] **Step 7: `npm test`, typecheck, oxlint, build. Commit** — `feat(rpc): отключение вкладки через Web Locks — порты закрытых вкладок больше не копятся`
