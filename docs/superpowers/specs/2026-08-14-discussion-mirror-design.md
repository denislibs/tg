# Зеркало поста канала в группе обсуждения

**Дата:** 2026-08-14
**Статус:** дизайн согласован
**Ворктри:** `.worktrees/discussion-mirror`, ветка `feat/discussion-mirror`
**Референс:** [`../../research/comments.md`](../../research/comments.md)
**Следующая работа поверх:** страница комментариев 1:1 (отдельная спека)

## Задача

В Telegram комментарии — это не отдельная сущность, а **обычный тред в группе
обсуждения**: сервер зеркалит каждый пост канала в связанную группу, и
комментарии отвечают на это зеркало. Отсюда всё, что видно в живом tweb:
плашка-родитель над лентой, сам пост первым баблом в треде, кнопка «перейти к
оригиналу», сервисное «Discussion started», глубокие ссылки `?comment=`.

У нас комментарий — это сообщение в группе с `thread_root_id = id поста в
канале`, а зеркала нет вовсе. Пока это внутреннее дело бэкенда, разницы не
видно; она вылезает ровно там, где tweb работает с тредом как с обычной
историей группы. Эта спека приводит данные к Telegram-модели.

## Решения (приняты при обсуждении)

1. **Зеркало создаётся на каждый пост**, как в Telegram: в истории самой группы
   обсуждения видны все посты канала, а тред существует ещё до первого
   комментария.
2. **Миграция создаёт зеркала только для постов, у которых уже есть
   комментарии**, и переводит их `thread_root_id` на зеркало. Полный бэкфилл
   истории не делаем.

## Модель данных

Зеркало — обычная строка `messages`. Почти все поля уже есть:

| поле | значение | зачем |
|---|---|---|
| `chat_id` | группа обсуждения | зеркало живёт в группе |
| `send_as_chat_id` | **канал** | автор бабла в UI — канал (Telegram) |
| `sender_id` | автор поста | аудит; в UI не показывается |
| `fwd_from_chat_id` | канал | «перейти к оригиналу» |
| `fwd_from_msg_id` | id поста | то же + резолв зеркала по посту |
| `fwd_date` | дата поста | атрибуция пересылки |
| `thread_root_id` | `NULL` | зеркало само — корень треда |
| `is_discussion_mirror` | `true` | **новая колонка**, отличает зеркало от обычной пересылки |
| `type`, `text`, `entities`, `media_id`, `grouped_id`, `poll_id`, … | копия поста | контент |

**Изменения схемы:**

1. колонка `messages.is_discussion_mirror boolean NOT NULL DEFAULT false`;
2. уникальный индекс `(chat_id, fwd_from_chat_id, fwd_from_msg_id) WHERE is_discussion_mirror`.

Колонка нужна именно для того, чтобы индекс не задел обычную пересылку: без неё
уникальность по `(chat_id, fwd_from_chat_id, fwd_from_msg_id)` запретила бы
переслать один и тот же пост канала в одну группу дважды — легальное действие
пользователя. Флаг делает уникальность применимой ровно к зеркалам: одно на
пост, гонка параллельных публикаций/ретраев закрыта, пересылки не затронуты.
Он же — единственный честный признак «это зеркало» для резолва
`MirrorByPost`: по `fwd_from_*` зеркало неотличимо от пересылки, сделанной
пользователем от имени канала.

## Создание

Точек вставки сообщения в канал четыре: `PostToChannel` (текстовый пост),
`Send` (пост с медиа), `Forward` (пересылка в канал), `suggested.go`
(одобренный предложенный пост). Все четыре после вставки зовут один usecase-хелпер:

```
mirrorChannelPost(ctx, post domain.Message) error
```

- канал не имеет привязанного обсуждения → тихий no-op (публикация не падает);
- вызов идёт **в той же транзакции**, что и сам пост: пост без зеркала — это
  пост без треда, расхождение недопустимо;
- альбом (`grouped_id`) зеркалится целиком, элемент к элементу; тред живёт на
  главном сообщении группы — как в tweb, где `replies` лежат на одном сообщении
  альбома;
- **доставка зеркала переиспользует обычный путь группового сообщения**
  (тот же веер по `MemberIDs`, что у `Send`), а не собственную копию логики:
  подписчики группы видят пост как новое сообщение, как в Telegram.

## Чтение

Наружу API не меняется — клиент по-прежнему оперирует `channelID` + `postID`.
Внутри появляется резолв:

- новый порт `MirrorByPost(ctx, channelID, postID) (int64, error)` и батч
  `MirrorsByPosts(ctx, channelID, postIDs) (map[int64]int64, error)`;
- `PostComment` резолвит зеркало и шлёт `Send(группа, ThreadRootID = id зеркала)`;
- `ListComments`, `CountThread`, `RecentThreadRepliers` считают по id зеркала;
- пост без зеркала (обсуждение выключено) — как сейчас: `domain.ErrNotFound`
  для `PostComment`/`ListComments`, пустые карты для `CommentCounts`.

## Миграция

Делится на две части — по тому, что чем проверяется.

**Схема — goose `0093_discussion_mirrors.sql`** (применяется на старте):
колонка `is_discussion_mirror` и уникальный индекс из раздела «Модель данных».

**Данные — идемпотентный Go-шаг** `BackfillDiscussionMirrors(ctx, pool) (int, error)`,
вызывается после `Migrate` там же, где уже вызывается `SeedDemo`
(`app/providers.go::providePool`):

1. найти пары (канал, пост), у которых есть хотя бы один комментарий
   (`messages.thread_root_id` указывает на сообщение канала) и у канала есть
   привязанная группа обсуждения;
2. вставить зеркало в эту группу с полями из таблицы выше; `seq` — продолжение
   счётчика группы, чтобы не конфликтовать с существующими сообщениями;
3. перевести `thread_root_id` этих комментариев на id созданного зеркала.

Почему Go, а не SQL внутри goose: миграцию с данными нечем проверить —
`NewTestDB` поднимает базу уже прогнанной, «старую форму» данных в неё можно
положить только после. Go-шаг вызывается тестом напрямую на засеянных данных, и
его идемпотентность (второй прогон ничего не меняет) — обычный тест, а не вера.
Порядок обязателен: схема раньше данных, поэтому шаг живёт после `Migrate`.

## Тесты (приёмка)

Интеграционные, на testcontainers (как остальной бэкенд):

- публикация поста в канал с обсуждением создаёт зеркало с правильными
  `send_as_chat_id` и `fwd_from_*`; в канале без обсуждения зеркала нет;
- все четыре пути вставки (`PostToChannel`, `Send` с медиа, `Forward`,
  одобрение предложенного поста) создают зеркало — по тесту на путь;
- повторная попытка зеркалить тот же пост не создаёт второго (индекс);
- **обычная пересылка не сломана**: один и тот же пост канала можно переслать в
  ту же группу дважды — индекс её не задевает (`is_discussion_mirror = false`);
- `MirrorByPost` не принимает за зеркало пользовательскую пересылку поста от
  имени канала в ту же группу;
- комментарий приземляется в тред зеркала; `ListComments`/`CountThread`/
  `RecentThreadRepliers` отдают его по (канал, пост);
- альбом: зеркалятся все элементы, тред один;
- миграция: на данных «пост + комментарии по старой схеме» создаёт зеркало и
  переводит `thread_root_id`; повторный прогон ничего не меняет;
- зеркало доставляется участникам группы обычным путём (веер по `MemberIDs`).

## Вне периметра

- Фронтенд не трогаем вовсе: страница комментариев 1:1 — отдельная спека поверх
  этой и поверх уже смерженного стека инстансов.
- Полный бэкфилл истории каналов в группы (решение 2).
- Сервисное сообщение «Discussion started» — оно генерируется клиентом локально
  (в tweb это temp-сообщение с дробным mid), сервер его не хранит.
- Удаление/редактирование поста → синхронизация зеркала: отдельная задача,
  здесь только создание. Зафиксировано осознанно, чтобы не раздувать периметр.
