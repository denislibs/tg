# Гигиена выката: номер сборки, регистрация SW и нехешированные скрипты воркера

**Статус:** открыт. Заведён 2026-09-07 веткой `fix/visible-cleanup` вместе с
починкой «пустая страница при F5 после выката».
**Что уже закрыто той же веткой:** воркер больше не кэширует и не отдаёт
оболочку (`public/sw.js`, ветка навигации снята — эталон tweb
`serviceWorker/index.service.ts:269-345`), `activate` сносит кэш оболочки
целиком (эталон `:357-359`), потолок кэша поднят выше размера одной сборки,
поиск в кэше идёт с `{ignoreVary: true}` (эталон `serviceWorker/cache.ts:20`).

Ниже — то, что вскрылось рядом и НЕ чинится правкой воркера.

## 1. Номер сборки заморожен на единице — и это ломает не только кэш

`web-client/package.json:5` — `"build": 1`, закоммичено. Поднять его должен был
бы деплой: `scripts/write-version.mjs:23` берёт
`Number(process.env.VITE_BUILD) || Number(pkg.build) || 1`. Проверено:
`VITE_BUILD` не выставляет ни один скрипт репозитория, воркфлоу
`.github/workflows` нет вовсе, Dockerfile'ы есть только у `backend/` и
`messenger_elixir/`.

Следствий два, и второе хуже первого:

* **имя кэша оболочки** (`app-shell-<build>`) не менялось никогда — из-за этого
  и была мертва прежняя очистка версий. Правкой воркера обезврежено: `activate`
  больше не смотрит на имя;
* **version-gate не срабатывает вовсе.** `core/version/versionCheck.ts` раз в 30
  минут тянет `public/version` и сравнивает с вкомпиленным
  `APP_VERSION_FULL`. Оба значения выводятся из одного и того же `build`,
  поэтому после выката они СОВПАДАЮТ, расхождения не возникает никогда, и
  кнопка «Обновить» пользователю не показывается ни разу. Порт
  (tweb `sidebarLeft/index.ts ~340-357`) написан правильно — не хватает только
  того, чтобы номер рос.

**Что делать:** поднимать `build` на выкате (env `VITE_BUILD` в пайплайне либо
инкремент в `package.json` релизным шагом). Правка процесса/конфига, поэтому
здесь названа, а не сделана.

## 2. Регистрация воркера не обрабатывает обновление

`web-client/src/client/boot.ts:86-88`:

```ts
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js').catch(() => { /* push unavailable */ })
}
```

Ни `updateViaCache`, ни подписки на `updatefound`/`controllerchange`, ни
`registration.update()`. У оригинала на этом месте целый блок восстановления
(`lib/apiManagerProxy.ts:671-698`): регистрация с `{type: 'module', scope: './'}`
и лечение случая «регистрация активна, а контроллера у документа нет» —
`registration.unregister()` + переход на тот же URL с параметром-счётчиком
`swfix` (не больше трёх раз).

Сам оригинал помечает это «! doubtful fix for hard refresh» (`:693`), и это
именно про жёсткое обновление — сосед по симптому нашей задачи. Портировать
стоит, но отдельно: цикл «разрегистрировались и перешли по URL» с ошибкой в
условии превращается в бесконечную перезагрузку, и его нужно ставить со своим
пином, а не прицепом.

## 3. `importScripts` нехешированных `/sw-bridge.js` и `/sw-stream.js`

`public/sw.js:8` и `:30` подключают `public/sw-bridge.js` / `public/sw-stream.js`
— единственные скрипты воркера БЕЗ контентного хеша в имени. Импортированные
скрипты попадают в script resource map регистрации, и «содержимое поменялось, URL
— нет» для них штатная ситуация. У tweb сам воркер — часть графа сборки
(`ServiceWorkerURL`, `apiManagerProxy.ts:671`), то есть хешируется вместе с ней.

Наш `sw.js` статичен намеренно (он вне графа Vite), но версионировать его
импорты можно — например, параметром запроса от `write-version.mjs`. Работа
небольшая, но упирается в пункт 1: параметром должен быть номер сборки.

## 4. `no-cache` не доезжает до SPA-фолбэка (nginx)

`nginx/nginx.conf` вешает `Cache-Control: no-cache` на `location = /index.html`,
а SPA отдаётся через `location / { try_files $uri $uri/ /index.html; }` —
внутренний `try_files`-фолбэк в блок `location = /index.html` НЕ заходит.
Поэтому на URL `/` уходит ответ без `Cache-Control`, только с ETag/Last-Modified,
и HTTP-кэш браузера вправе считать его свежим эвристически.

После снятия SW-кэша оболочки это перестало давать пустую страницу (документ
идёт в сеть и получает 304/200 по валидатору), но остаётся лишним окном на
задержку выката. Правка — в конфиге nginx, поэтому здесь названа, а не сделана.
