запуске файла в одиночку:

## Частота и условия воспроизведения (перепроверено на этой ветке)

Ветка поднята от свежего `origin/main`, зависимости — чистый `npm ci`.

- Полных прогонов `npx vitest run`: 4.
  - Прогон №1: зелёный (583/583 файлов).
  - Прогон №2: зелёный (583/583 файлов).
  - Прогон №3: **упал именно этот тест** (582 passed | 1 failed), сообщение
    выше — дословно.
  - Прогон №4: зелёный (583/583 файлов; в нём вместо этого поймался другой,

- Изолированный запуск (`npx vitest run src/core/net/wsClient.test.ts`):

Итог: 1 падение из 4 полных прогонов, 0 падений из 2 изолированных — флейк
живой, воспроизводится под нагрузкой параллельного прогона, как и было
описано ранее («падал под нагрузкой у нескольких исполнителей, изолированно
зелёный»).

## Установленная причина

`WsClient.connect()` (`web-client/src/core/net/wsClient.ts:34-36`) при
включённом TL-флаге запускает НАСТОЯЩИЙ динамический импорт кодека:

```ts
if (this.tlWire && !this.decodeTL) {
  void import('./tlFrames').then((m) => { ... })
}
```

Пока промис не резолвился, входящие кадры складываются в очередь
(`wsClient.ts:52`, `this.queued.push(data)`), а тест ждёт их разбора через
`vi.waitFor(() => expect(got).toHaveBeenCalledTimes(2))`
(`wsClient.test.ts:93`) — БЕЗ `vi.useFakeTimers()` в файле, то есть с реальными
таймерами и реальным резолвом промиса.

`vi.waitFor` по умолчанию у vitest — бюджет 1000 мс с опросом каждые 50 мс
(нигде в файле и в `vitest.config.ts` не переопределён). В обычных условиях
`import('./tlFrames')` резолвится за миллисекунды. Под тяжёлой параллельной
нагрузкой полного прогона (583 файла, конкуренция за CPU между воркерами)
реальное время до резолва динамического импорта и до исполнения `.then`
может вылезти за этот бюджет чисто по загрузке — тест ловит `got` ещё не
вызванным ни разу (`"got 0 times"` в упавшем прогоне — то есть промис не
успел резолвиться вообще, не «частично»).

Изолированный прогон (0 конкуренции за CPU) укладывается в бюджет всегда —
это согласуется с «6 из 6 / 2 из 2 зелёный изолированно».

## Почему это не регрессия конкретной ветки

Механизм — фиксированный wall-clock бюджет ожидания реального `import()` —
не зависит от содержимого какой-либо рабочей ветки; он воспроизведён на
ветке, поднятой от свежего `origin/main`, без единой правки кода. Ранее
описывался как «падал у нескольких исполнителей» — то же самое явление,
подтверждено заново.

## Почему не починено на месте (хотя выглядит как «10 минут»)

Формально самое дешёвое лечение — поднять `timeout` у `vi.waitFor` на строке
93 (например до 5000 мс). Это снижает вероятность, но НЕ убирает гонку
структурно: при достаточно тяжёлой нагрузке лимит можно исчерпать снова —
разница только в пороге. Учитывая, что задача прямо просит фиксировать факты,
а не подбирать эвристический лимит без возможности доказать мутацией, что
конкретное число окончательно устраняет проблему, — оставлено долгом, а не
починкой на месте.

## Что нужно сделать для починки

1. Минимальный вариант: поднять `timeout` у `vi.waitFor` на строке 93 с
   дефолтных 1000 мс до величины с запасом под загруженный CI (например
   5000 мс) — снижает частоту, не устраняет гонку структурно.
2. Структурный вариант: не полагаться на wall-clock ожидание реального
   `import()` в этом тесте — например, дать `WsClient` тестовый крюк
   (например, принимать инжектируемый loader вместо жёстко зашитого
   `import('./tlFrames')`), чтобы тест мог управлять моментом резолва явно
   (через собственный контролируемый `Promise`), как это уже сделано для
   `WebSocket` через `FakeWS`.

## Как проверить, что починено

10+ полных прогонов `npx vitest run` подряд без единого падения именно этого
теста; в идеале — с искусственной нагрузкой CPU параллельным процессом на
время прогона, чтобы подтвердить устойчивость под реальным давлением, а не
статистическую удачу.

- `web-client/src/core/net/wsClient.ts:34-36,52` — источник реального
