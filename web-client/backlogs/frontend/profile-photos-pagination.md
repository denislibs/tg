# Пагинация галереи своих/чужих фото — ручка отдаёт всё одним ответом

**Статус:** открыт, долг назван (не закрыт кодом). Правится БЭКЕНДОМ (новая
форма ручки), а не подгонкой клиента.
**Дата фиксации:** волна 3 «Solid-миграция», программа `docs/superpowers/
plans/2026-09-05-profile-avatars-class.md`, задача 2 (данные и лента
`PeerProfileAvatars`), ревью задачи 6 — 2026-09-05.
**Контекст:** `components/peerProfileAvatars.ts::setPeer`, ветка
`isUser(peerId)`, `ListLoader.loadMore` (строка с комментарием «Плановое
расхождение задачи 2… ручка отдаёт ВЕСЬ список одним ответом»).

## Что в tweb

`ListLoader({loadCount: 50, loadMore, ...})` (`peerProfileAvatars.ts:433
-521`) для пользователя грузит историю аватаров ПОСТРАНИЧНО:
`appPhotosManager.getUserPhotos(peerId, maxId, loadCount)` — `maxId` это id
последнего уже загруженного фото (курсор), сервер отдаёт следующие
`loadCount` штук СТАРШЕ него. `ListLoader` дёргает `loadMore` повторно по
мере прокрутки/долистывания карусели (`loadWhenLeft`), не заказывая весь
список сразу.

## Чего нет у нас

`GET /users/{id}/photos` (`profileManager.ts:110`,
`backend/.../profile_handler.go:438-461` → `ListProfilePhotos`) не принимает
ни курсора, ни лимита — всегда отдаёт ВСЮ галерею одним массивом. Наш
`ListLoader` в порту подключён как в оригинале, но `loadMore` физически не
может запросить «ещё» у сети: он просто отдаёт остаток уже полученного
единым ответом массива одной второй «страницей» (`restServed` флаг), и на
этом ресурс исчерпан — дальнейшие вызовы `loadMore` возвращают пустой
список.

## Эффект сегодня

Функционально не заметно ПОКА галерея небольшая: весь список и так
загружается за один HTTP-запрос при открытии профиля, лента листается без
видимых пауз. Разница проявится на больших галереях (у активных
пользователей — сотни фото за годы): каждое открытие профиля тянет ВЕСЬ
список целиком (метаданные, не байты) вместо первых 50, а `loadWhenLeft` /
`LOAD_NEAREST`-механика ленивой подгрузки байтов работает по факту как
раньше, но экономии на МЕТАДАННЫХ, которую даёт постраничность оригинала,
нет.

## Что делать

1. Бэкенд: `GET /users/{id}/photos` принимает `?before_id=`/`?limit=`
   (курсор — id последнего полученного фото, как у `getUserPhotos` в
   оригинале) и отдаёт следующую порцию, а не всё сразу. Не ломать текущий
   контракт «без параметров = всё» резким изменением — либо версионировать,
   либо считать отсутствие параметра как «первая страница» с разумным
   лимитом по умолчанию (сверить с ожиданиями существующих потребителей
   ручки, если такие есть, кроме этой карусели).
2. `core/managers/profileManager.ts::listPhotos` — сигнатура
   `listPhotos(userId, cursor?, limit?)`, отдаёт `{items, nextCursor}`.
3. `components/peerProfileAvatars.ts::setPeer` — `loadMore` зовёт
   `listPhotos` заново с курсором вместо отдачи хвоста уже полученного
   массива; убрать флаг `restServed`, он был костылём именно под
   не-постраничную ручку.

**Критерий готовности:** открытие профиля с галереей, которая физически
превышает один «разумный» лимит страницы, не тянет её целиком одним
запросом — метаданные догружаются по мере пролистывания/приближения к
концу ленты, как в оригинале; тест на `peerProfileAvatars.test.ts`
заводит фейковый `listPhotos` с курсором и проверяет, что `loadMore`
передаёт курсор ПОСЛЕДНЕГО полученного элемента, а не отдаёт статичный
хвост.
