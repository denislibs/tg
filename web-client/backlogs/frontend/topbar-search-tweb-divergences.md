## 1. Нет гейта `liteMode` на длительность анимации — РАСХОЖДЕНИЕ

tweb `chat.ts:746-748`:

```ts
const animate = liteMode.isAvailable('animations');
const options: KeyframeAnimationOptions = {
  fill: 'forwards', duration: animate ? 200 : 0, easing: 'ease-in-out'
};
```

При выключенных анимациях (lite mode / экономия батареи / `prefers-reduced-motion`)
переход у tweb **мгновенный**, `duration: 0`. У нас 200 мс захардкожено:

```ts
const options: KeyframeAnimationOptions = { fill: 'forwards', duration: 200, easing: 'ease-in-out' }
```

**Почему не починил сразу:** `web-client/src/helpers/liteMode.ts` — заглушка с
`@ts-nocheck`, в ней только `export type LiteModeKey = string`, а в комментарии прямо
сказано: «реального lite-mode гейтинга (через настройки) пока нет; полная версия tweb
завязана на solid-store настроек и переносится позже». То есть это не дефект поиска, а
общепроектный пробел: гейта нет нигде, точечная заплатка здесь только создала бы
единственное в проекте место со своей логикой.

**Что делать:** чинить вместе с портом подсистемы настроек/lite-mode. Тогда пройтись по
всем `duration: 200` в анимациях и завести общий хелпер вида
`animationDuration(200)` → `liteMode.isAvailable('animations') ? 200 : 0`.

**Затрагиваемые файлы:** `src/helpers/liteMode.ts` (реальная реализация),
`src/components/conversation/ChatHeader.tsx` (и все прочие места с хардкодом длительности).

поиск умеет открываться **уже настроенным**, и tweb пользуется этим из пяти мест:

| Точка входа | tweb | Что открывается | Есть у нас |
|---|---|---|---|
| Клик по хэштегу в сообщении | `internalLinkProcessor.ts:114` | `{query: '#'+hashtag+' '}` | нет |

| Клик по тегу-реакции в бабле | `bubbles.ts:3272` | `{reaction}` | нет |

булева (`setOpen(chatId, open)`) — передать `query`/`filterPeerId`/`reaction` было
физически нечем. **Это уже исправлено:** стор получил
`initSearch(chatId, {query?, filterPeerId?, reaction?})` / `closeSearch(chatId)`,
панель засевается из затравки. Осталось позвать `initSearch` с параметрами из пяти

Обиднее всего с хэштегами: режим хэштег-поиска в `useChatHeaderSearch` портирован

### 2б. Переоткрытие во время анимации ухода — старый запрос остаётся

**Как в tweb.** Эффект возвращает узел как «предыдущее значение», и в ветке закрытия
оба `return` отдают `undefined`:

```ts
createEffect<HTMLElement>((topbarSearch) => {
  if(!needSearch()) {
    if(!topbarSearch) return;                                  // → prev = undefined
    animateElements(topbarSearch, false).then(() => {
      topbarSearch.remove();                                   // снимается ЗАХВАЧЕННЫЙ узел
    });
    return;                                                    // → prev = undefined
  }
  topbarSearch = untrack(() => TopbarSearch({...})) as HTMLElement;  // ВСЕГДА новый узел
  this.topbar.container.append(topbarSearch);
  animateElements(topbarSearch, true);
  return topbarSearch;
});
```

Значит при переоткрытии до конца 200-мс анимации ухода tweb создаёт **новый**
`TopbarSearch`, а старый ещё живёт в DOM и удалится своим `.then`. Коротко существуют
два `.topbar-search-container` одновременно. Плюс `onClose` дёргает
`this.searchSignal(undefined)`, а `query`/`filterPeerId`/`reaction` — сигналы уровня
`chat.ts`, так что новый узел поднимается с **пустым** полем.

**Как у нас.** Счётчик `runRef` отменяет протухшее размонтирование, поэтому узел
**переиспользуется** — React его не размонтировал. А всё состояние поиска (`text`,
`value`, `filterPeerId`, `reaction`, `targetIdx`) — локальные `useState` внутри
`useChatHeaderSearch`, то есть живут ровно столько, сколько смонтирован компонент.
Итог: при быстром переоткрытии (внутри окна 200 мс) у нас в поле остаётся **старый
запрос**, у tweb — пусто.

**Насколько заметно:** только в окне 200 мс. При обычном переоткрытии узел уже
размонтирован, состояние сбрасывается, поведение совпадает с tweb. Сам по себе пункт 2б
косметический — но лечится он ровно тем же, чем 2а.

## 3. Web Animations копятся и никогда не отменяются — СОВПАДАЕТ с tweb

Каждый цикл открыть/закрыть вешает на `.content`, `.chat-utils` и контейнер поиска новую
анимацию с `fill: 'forwards'`, и ни одна не снимается (`cancel()` не вызывается ни у нас,
ни в tweb). За N циклов на элементе накапливается 2N заполняющих анимаций; итоговое
значение берётся от последней, поэтому визуально всё корректно — замер после трёх циклов
показал `opacity: 1` и ровно 6 вызовов `animate` на цикл, без дублей.

**Это НЕ расхождение** — tweb ведёт себя точно так же (`chat.ts:756-759`), поэтому чинить
в одностороннем порядке нельзя: любая «уборка» станет отступлением от эталона и должна
быть помечена `// отступление от tweb: <причина>`.

**Когда всё же стоит вернуться:** если профилировщик покажет заметный рост числа
активных `Animation` на длинной сессии (много открытий поиска). Тогда — осознанное
отступление: держать ссылки на созданные `Animation` и звать `cancel()` у предыдущих
перед запуском новых.

## Критерии готовности (для пунктов 1 и 2)

- При выключенных анимациях открытие/закрытие поиска происходит мгновенно (`duration: 0`),
  без промежуточных кадров.
- Переоткрытие поиска в любой момент (в т.ч. на 100 мс после Escape) даёт **пустое** поле
  ввода, как в tweb.
- Регрессии нет: закрытие по-прежнему проигрывает ровно один переход — 3 вызова `animate`,
  `opacity` у `.content` растёт монотонно `0 → 1` за ~200 мс и не сбрасывается.
- `npm run typecheck` чистый, `npm test -- --run` зелёный, проверка на стенде `:38443`.

## Как проверять (методика, которой ловили исходное мерцание)

Инструментировать `Element.prototype.animate` и сэмплить `opacity` по `requestAnimationFrame`:

```js
const orig = Element.prototype.animate;
const log = [];
Element.prototype.animate = function(kf, opts) {
  const cls = String(this.className?.baseVal ?? this.className ?? '');
  if (/(^|\s)(content|chat-utils|topbar-search-container)(\s|$)/.test(cls)) {
    log.push({ cls, kf: JSON.stringify(kf), before: getComputedStyle(this).opacity });
  }
  return orig.call(this, kf, opts);
};
```

Признак дефекта: у `.content` больше одного вызова на переход, либо вызов с кадром
`{opacity: 0}` в начале при уже `before === "1"` — это и есть второе мигание.
